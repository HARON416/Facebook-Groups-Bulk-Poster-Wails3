Postika uses [Wuchale](https://wuchale.dev/adapters/svelte/) with its Svelte adapter.
The Vite plugin extracts UI text into Gettext PO catalogs and bundles compiled
catalogs with the desktop app. Translations work offline; changing languages
does not call a translation service.

Choose a language from the top bar or Settings. This is an app-wide preference,
shared across accounts and synchronized with open settings/log windows. English
is the initial language. The selected language is saved in the webview's local
storage under `postika:language`. Unsupported stored values fall back to English.
The HTML `lang` attribute, date formatting, and Arabic text direction update
with the selected language. Account names, Facebook group names, drafts,
attachments, API keys, and rewrite instructions remain user data. The built-in
`default` profile's original “Default profile” name is a translated display
label; its saved name and ID stay stable. Custom names stay unchanged, including
custom accounts named “Default profile”. The shared helper in
`frontend/src/components/AccountLabel.svelte` is included in Wuchale extraction.
It uses a Svelte module block so the adapter generates the runtime lookup for
the exported helper, which also makes language changes reactive at each call.

Settings and Posting logs use the same custom window controls as the main
window. Their draggable titlebars display the translated window name and account
label, and update the native taskbar/window-switcher title when the language
changes. Posting logs share one window with the translated account switcher;
changing its selection also updates the native title. Settings remain bound to
the account that opened them. Closing still hides the retained window,
preserving its session.

The theme picker’s heading, search field, empty state, and close button are
translated. Palette names remain as supplied (for example, Catppuccin and
Terminal), and Postika Light / Postika Dark identify the original palettes.

All 32 supported languages have translations for every extracted interface
message, including help text, notifications, editor controls, scheduling, and
Settings. The catalogs include machine-assisted translations; review wording
and terminology in context when making language-specific improvements.
Go-generated errors, progress messages, and Facebook diagnostics also remain in
their original language. These diagnostics are separate from interface copy.

The source of truth is `frontend/src/locales/<locale>.po`. To update translations:

1. Run `npm --prefix frontend run i18n:extract` after changing UI text.
2. Edit `msgstr` entries in the relevant PO catalog. Preserve numbered arguments
   such as `{0}` and markup slots such as `<0/>` or `<0>…</0>`.
3. Run `npm --prefix frontend run i18n:check` to validate messages and placeholders.
4. Run `npm --prefix frontend run check` and `npm --prefix frontend run build`.

`npm --prefix frontend run i18n:status` reports untranslated entries per locale.
The validation command checks consistency and requires complete catalogs for
every language listed in `languages.js`. It reports each language's translated
message count. `npm --prefix frontend run i18n:coverage` runs the coverage check
on its own. Missing or fuzzy translations and longer messages copied unchanged
from English fail the check. Short shared terms such as Gemini remain valid.
Both `npm run check` and `npm run build` extract messages and enforce coverage
before continuing, so new interface copy needs translations in every catalog.
Vite extracts and compiles automatically during development and production
builds. The normal frontend check also regenerates catalogs first, so it works
in a fresh checkout.

`frontend/src/locales/.wuchale/` is generated and ignored. Commit PO files,
`languages.js`, `data.js`, `plural.js`, and the loader alongside configuration
changes. To add another language, add its BCP 47 code, native name, and flag to
`languages.js`, run extraction, and translate the new catalog.

The extraction heuristic in `frontend/wuchale.config.js` excludes keyboard
identifiers and comparisons against English backend diagnostics. The SVG icon
table is also excluded. UI label/description properties are explicitly included
so workflow steps and login guidance update when the locale changes. For
exceptional strings, Wuchale supports `/* @wc-ignore */`, `/* @wc-include */`,
and their HTML-comment equivalents. Never mark selectors, event names, protocol
constants, editor state, or user content as translatable text.

The posting interval labels use separate text spans around their inputs. This
avoids an invalid nested snippet emitted by the current Wuchale adapter for the
original mixed text/input markup; the browser integration suite exercises both
the posting form and Settings to catch regressions here.

Posting log translations use `components/LogMessage.svelte`, a module helper
that resolves messages when rendered so historical entries update immediately
when the language changes. `lib/log-message.ts` parses known backend templates;
`lib/log-messages.json` maps exact backend phrases to stable translation keys.
When adding a Go log phrase, add its mapping and the matching localized return
value in the helper, then update every catalog. Variable templates keep group
names, links, and error codes as data. Counts and scheduled dates use the active
locale. Unrecognized external diagnostic text and original Facebook responses
remain intact under Debug details; raw response copying is unchanged. Run
`npm --prefix frontend run logs:test` for parsing checks and the posting logs
browser test for language changes on existing entries.
